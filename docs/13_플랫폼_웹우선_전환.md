# 13. 플랫폼 결정 변경 — 웹 우선, 이후 앱스토어·구글플레이 (2026-09-11)

docs/05의 "앱인토스 미니앱 주력" 전제를 바꾼다. 이 문서가 플랫폼에 관해서는 05보다 우선한다.

## 바뀐 결정

**웹(반응형) 먼저 열어 데이터를 쌓고 → 구매·예약 기능을 붙여 → 앱스토어·구글플레이에 출시한다.**

앱인토스는 후순위로 미룬다. 버리는 것은 아니고, 코드가 그대로 갈 수 있게 유지한다.

## 왜 바꿨나

| 항목 | 앱인토스 | 스토어 |
|---|---|---|
| 실물 술 결제 | 토스페이만 | 외부 결제 자유, 실물 상품은 인앱결제 30% 면제(애플 지침 3.1.5) |
| 로그인 | 토스 로그인만 | 자유 |
| 주류 정책 | 개발자센터 문서에 **명문 규정 없음** | 술담화·데일리샷 등 전통주 앱 선례 존재 |
| 심사 | 1~3개월, 2026년 기준 강화(기존 미니앱 재심사 포함) | 애플 수일 / 구글은 신규 개인 계정에 테스터 12명·14일 비공개 테스트 선행 |
| 획득 | 토스 앱 내 노출, 설치 불필요 | 설치 필요 |

- **결제**가 결정적이다. 최종 목표가 전통주 판매인데 앱인토스는 실물 상품에 토스페이만 허용한다.
- **불확실성이 토스 쪽에 있다.** 주류 취급 가능 여부가 문서에 없어서, 1~3개월 심사 후 거절되거나 통과 후 정책이 바뀔 수 있다. 스토어는 같은 사업 모델의 선례가 이미 있다.
- **획득은 토스가 유리**하지만, 그 이점은 판매를 못 하면 의미가 줄어든다.

## 전환 비용이 낮은 이유

앱인토스 SDK를 쓰는 파일이 3개뿐이다 — `lib/location.ts` · `lib/openExternal.ts` · `lib/analytics.ts`.
나머지는 서버 없이 도는 정적 번들이고, 이미 `inToss()`로 환경을 갈라 처리한다. CLAUDE.md 규칙으로 SDK를 한곳에 가둬 온 결과다.

## 두 화면을 나눈다

| | 공개 웹 (`apps/web`) | 앱 (`apps/miniapp`) |
|---|---|---|
| 렌더 | Next.js 서버 렌더 | 클라이언트 SPA |
| 폭 | 반응형 (모바일~데스크톱) | 모바일 고정 430px |
| 역할 | 검색 유입 수신, 색인 | 그대로 토스·스토어 앱이 됨 |
| 공유 | `packages/shared` (데이터·검색·점수) | 〃 |

미니앱을 데스크톱까지 넓히지 않는다. 어차피 앱이 될 화면이라 되돌려야 한다.

## 애플 4.2 (최소 기능) 주의

애플은 웹사이트를 그대로 감싼 앱을 거절한다. "사파리에서 열었을 때와 다를 게 없으면 앱일 이유가 없다"가 기준이다. 구글은 관대하다.

따라서 **추천 기능만 있는 상태로 애플에 올리면 위험하다.** 푸시 알림(주문 상태·예약 확정), 오프라인 열람(저장한 페어링), 위치(이미 있음) 중 최소 하나는 실제로 동작해야 한다. 구매·예약을 붙이면 푸시가 자연히 필요해지므로, 커머스 구현이 곧 4.2 통과 근거가 된다.

## 진행 순서

1. **공개 웹 페이지** — 서버 렌더·반응형 (2026-09-11 1차 완료, 아래 참고)
2. **유입 만들기** + 사업자 등록·통신판매업 신고 병행 (신고가 임계 경로다)
3. **PWA** — manifest·서비스 워커. 홈 화면 추가와 오프라인 열람의 기반
4. **구매 기능** — 데이터로 입점 우선순위를 정한 뒤. 푸시 알림 함께
5. **스토어 출시** — 구글 먼저(테스터 12명·14일 선행), 애플은 네이티브 기능을 갖춘 뒤
6. **식당 예약** — 구매가 돌아간 다음. 구매와 동시에 영업하지 않는다

앱인토스는 4번 이후 여력이 되면 같은 번들로 재개한다. 그 전에 토스 정책팀에 주류 취급 가능 여부를 문의해 두면 판단이 쉬워진다.

## 1차 구현 (2026-09-11)

`apps/web`에 공개 웹을 붙였다. 라우트 그룹 `(site)`.

| 경로 | 내용 |
|---|---|
| `/` | 랜딩 — 인기 전통주·음식, 카탈로그 규모 |
| `/drinks` | 전통주 목록 (종류별) |
| `/drinks/[slug]` | 전통주 상세 — 어울리는 음식 전체, 추천 이유, 근거 인용문·출처 링크, 구매 링크 |
| `/foods` | 음식 목록 (분류별) |
| `/foods/[slug]` | 음식 상세 — 어울리는 전통주 전체 |
| `/sitemap.xml` · `/robots.txt` | 색인 (221 URL) |

- **슬러그는 한글**이다. `/drinks/복순도가-손막걸리` — 검색 키워드가 URL에 남는다. 경로 앞부분(`drinks`·`foods`)은 영문인데, **한글 경로 세그먼트는 Next.js 정적 생성에서 `InvalidCharacterError`로 깨진다**(실측). 슬러그(동적 구간)는 한글이어도 문제없다.
- 조회는 `slugKey()`로 기호·하이픈을 무시하고 맞춘다(`packages/shared/src/slug.ts`). DB의 `slug` 컬럼과 같은 형태라 그대로 대조된다.
- 제목을 검색어에 맞췄다: "복순도가 손막걸리에 어울리는 안주 28가지". 설명·canonical·OG 포함.
- 근거가 붙은 추천과 맛 프로필로 계산한 추정을 화면에서 구분한다(docs/12 A1 대응의 일부).
- 만 19세·음주 경고 문구는 전 페이지 푸터.
- 루트 레이아웃이 `body`에 라이트 색을 인라인으로 고정하고 있어 다크 모드에서 헤더 글자가 안 보였다. 색 지정을 각 구역 CSS(`site.css`·`admin.css`)로 옮겼다.

**검증** [실측] — 빌드 통과, 7개 경로 모두 200. 상세 페이지 HTML에 페어링 카드 28개·추천 이유·근거 인용문·경고 문구가 **서버에서 렌더된 상태로** 포함(64KB). 사이트맵 221건. 데스크톱 1280px과 모바일 375px 화면 확인.

**남은 일** — PWA(manifest·서비스 워커), 검색 기능(공개 웹), 지역별 페이지, 구조화 데이터(JSON-LD), 도메인 연결 후 `SITE_URL` 환경변수 설정.

## 간편로그인 (2026-09-12)

카카오 · 네이버 · 구글. **Supabase Auth는 네이버를 지원하지 않아** 세 곳 모두 공식 provider가 있는 **Auth.js v5**(`next-auth@beta`)를 썼다.

- 세션은 JWT 쿠키. 로그인할 때 우리 `users` 행을 upsert하고 그 id를 토큰에 넣는다(마이그레이션 0007).
- **키가 없는 공급자는 화면에서 빠진다.** 한 곳만 등록해도 그것만 동작하고, 전부 없으면 안내 문구가 나온다.
- 헤더의 로그인 상태는 **클라이언트에서** 세션을 가져온다. 서버 컴포넌트에서 `auth()`를 부르면 공개 페이지가 전부 동적 렌더로 바뀌어 검색 유입용 정적 생성이 깨진다.
- 로그인이 실제로 하는 일: **저장(찜)**. 술·음식 상세의 저장 버튼과 `/saved` 목록. 비로그인은 로그인 페이지로 보낸다.
- `next` 파라미터는 내부 경로(`/`로 시작)만 허용 — 오픈 리다이렉트 방지.

**등록해야 할 것** (사용자 작업)

| 공급자 | 콘솔 | 콜백 URL |
|---|---|---|
| 카카오 | developers.kakao.com → 카카오 로그인 활성화, 보안 Client Secret 발급 | `{도메인}/api/auth/callback/kakao` |
| 네이버 | developers.naver.com → 애플리케이션 등록 → 네이버 로그인 | `{도메인}/api/auth/callback/naver` |
| 구글 | console.cloud.google.com → 사용자 인증 정보 → OAuth 클라이언트 ID(웹) | `{도메인}/api/auth/callback/google` |

키는 `apps/web/.env.local`의 `AUTH_{KAKAO,NAVER,GOOGLE}_{ID,SECRET}`에. `AUTH_SECRET`은 이미 생성해 두었다.

**⚠ 공개 전 필수** — 로그인은 닉네임·이메일을 받으므로 **개인정보처리방침과 수집 동의**가 있어야 한다(개인정보보호법). 나중에 주문을 받으면 주문자 정보를 양조장에 넘기므로 **제3자 제공 동의**도 따로 받아야 한다(통신판매중개 구조).

**검증** [실측] — 임시 키를 넣고 세 공급자 모두 실제 인가 주소로 302 이동하는 것을 확인했다(`kauth.kakao.com` · `nid.naver.com` · `accounts.google.com`). 콜백 경로 3개 정상. 확인 후 임시 키는 지웠다.

## 회원 기능 (2026-09-12)

캐치테이블·데일리샷의 회원 동선을 참고했다. **이메일 회원가입**을 더해 소셜 키가 없어도 가입·로그인이 된다.

### 이메일 가입·로그인
- Auth.js의 Credentials 공급자. 비밀번호는 **Node 내장 scrypt**로 해시한다(외부 의존성 없음, `lib/password.ts`).
- 규칙: 8자 이상, 숫자만/같은 문자 반복 금지. 비교는 `timingSafeEqual`.
- **연속 실패 잠금** — 10회 실패하면 15분(`users.failed_attempts`·`locked_until`). scrypt가 느려도 무차별 대입을 늦추는 장치가 하나는 필요하다.
- 없는 계정도 해시 검증을 한 번 돌려 응답 시간을 비슷하게 맞춘다(계정 존재 여부 노출 방지). 실패 문구는 이메일·비밀번호를 구분하지 않는다.
- 가입하면 바로 로그인되고 `/my`로 간다. `next` 파라미터는 내부 경로만 허용.

### 하트(찜)와 마이페이지
- 저장 대상: **전통주 · 음식 · 음식점** (마이그레이션 0008에서 `saved_items.kind`에 `place` 추가).
- 음식점은 카탈로그에 없고 카카오 로컬에서 오므로 이름·주소·전화·링크·분류와 **어느 음식을 보다 저장했는지**를 `meta`(jsonb)에 함께 담는다.
- 하트는 목록 카드 오른쪽 위(아이콘)와 상세 버튼 두 모양. 비로그인이면 로그인으로 보내고 돌아온다.
- `/my` — 탭 3개(전통주·음식·음식점)와 각 개수. 빈 상태에는 둘러보기 버튼. 예전 `/saved`는 `/my`로 영구 이동.
- **맛집 찾기** — 음식 상세에서 "내 주변" 또는 지역을 누를 때만 카카오를 부른다. 페이지를 열 때마다 부르면 유료 쿼터가 금방 소진된다. 위치를 거부하면 지역 선택으로 넘어간다.

### 검색·구매·주변 판매점 (2026-09-12)

1차 공개 웹에 빠져 있던 것. 미니앱에는 있었는데 웹에 옮기지 않았다.

- **검색** `/search?q=` — 미니앱과 같은 엔진(`packages/shared/search`)을 서버에서 돌린다. 이름 매칭·상황 검색("매운 안주에 어울리는 술" → 조건 칩 + 근거 있는 순위)·비슷한 이름 제안. 헤더에 검색창(자바스크립트 없이 동작하는 GET 폼), 좁은 화면에서는 검색 링크. 검색 결과의 '둘러보기'(종류·지역·양조장)는 `/drinks?category=|region=|brewery=`로 간다.
- **지역 옵션**(2026-09-12 복원) — 검색 폼의 지역 선택(전국·수도권·부산·제주·울산·경남·대구·경북·강원·대전·충남/충북·세종·전남/전북, `packages/shared/src/regions.ts` TOP_REGIONS)과 같은 칩. `?region=busan`처럼 지역 id로 넘어가고 술 결과만 그 지역으로 거른다(음식은 지역 없음). 검색어 없이 지역만 고르면 그 지역 술 목록. `/drinks?region=<id>`도 같은 칩으로 거른다(종류 필터와 겹쳐 씀). 헤더 검색창은 고른 지역을 숨은 값으로 유지.
- **관심지역**(2026-09-12, 캐치테이블 참고) — 헤더 아래 줄 "📍 서울 ▾ · 현재 위치로". 누르면 관심지역 설정 화면(`RegionSheet`): 현재 위치로 설정(브라우저 위치 → `estimateRegion`), 인기 지역 5곳, 최근 설정 지역, 왼쪽 상위 지역/오른쪽 세부 지역. 수도권은 수도권 전체 › 서울 전체·강남·서초·잠실/송파/강동·… › 인천 › 경기도 전체·경기북부·수원·… 세 단계(구조는 `level2Of`/`childrenOf`, 데이터는 평평). 한 곳만 고른다. 저장은 기기(localStorage `pg_region`, `RegionProvider`), 로그인과 무관. 완료를 누르면 검색·전통주 목록이면 그 지역으로 다시 열고 다른 화면이면 전통주 목록으로. URL에 지역이 없고 관심지역이 있으면 검색·목록은 관심지역으로 연다(URL의 지역이 우선 — 공유 링크). 지역 칩은 최대 3단. 주변 식당·판매점의 지역 버튼도 관심지역을 먼저 보여 준다(예전 "연남·이태원" id는 지역 정의에 없어 전국 검색이 되던 버그 수정). 동 단위 지역에 양조장이 없으면 상위(서울) 기준으로 보여 주고 그 사실을 적는다. 클라이언트 컴포넌트는 `@pairinggo/shared/regions`만 가져온다(데이터 JSON이 번들에 들어가지 않게).
- **전통주 목록 종류 탭**(2026-09-13, 사용자 결정) — `/drinks`는 종류를 한 화면에 이어 붙이지 않고 탭으로 나눠 한 종류만 보여 준다(미쉐린·우리술품평회 연도 탭과 같은 방식). 탭 = `?category=`, 없으면 가장 많은 종류(탁주). 탭은 지역·양조장 조건을 건 뒤의 종류와 개수이고, 옮겨도 지역·양조장은 유지. 고른 종류가 그 지역에 없으면 첫 종류를 보여 주고 문구로 알린다. 지역 칩(알약)과 헷갈리지 않게 밑줄형 탭을 지역 칩 위에 둔다. 모바일은 가로로 밀고 오른쪽 끝을 흐리게. 종류마다 한 줄 설명.

### 상태 관리에서 걸린 것
앱 라우터는 화면을 옮겨도 레이아웃을 다시 만들지 않는다. 그래서 로그인 직후에도 헤더가 "로그인"인 채로 남았다. 세션과 저장 목록을 `SavedProvider` 한곳에서 관리하고 **경로가 바뀌면 다시 확인**하도록 고쳤다. 헤더와 하트가 같은 상태를 본다.

- **먹어봤어요** — 카드마다 어울렸다·보통·별로(`TriedRating`). 같은 버튼을 다시 누르면 취소, 다른 버튼이면 바꾼다. 회원 1명당 조합 1표(`pairing_ratings`, 0014, unique user·drink·food, 탈퇴 시 삭제). 비로그인이면 로그인 화면으로 보냈다가 `#pairings`로 돌아온다.
- **요약 문구** `pairing/ratings.ts` `summarizeRatings`: 0명 "아직 평가가 없어요" · 3명 미만 "먹어본 사람 N명"(판정 안 함) · 어울렸다 60% 이상 "12명 중 9명이 어울렸다(75%)" · 별로 50% 이상 "별로라는 평이 많아요" · 그 밖 "호불호가 갈려요". 정렬용 윌슨 하한(`wilsonLower`)도 함께 둔다(적은 표본의 100%가 많은 표본의 90%를 이기지 않게).
- **API** `/api/ratings` — GET `?drink=d01` 또는 `?food=f02` → 조합별 집계 + 내 평가(누가 뭐라고 했는지는 주지 않는다), POST `{d, f, rating|null}` 로그인 필수·같은 출처만. 세션은 `getToken`(auth()의 쿠키 재기록 경합 회피). 상세 화면은 캐시된 HTML이라 평가는 브라우저에서 `RatingsProvider`가 화면당 한 번 받는다. 이벤트 `rate`{d, f, rating}.

**검증** [실측] — 복순도가 손막걸리 31조합 = 전문가픽 3·대중픽 11·맛 분석 17, 전문가픽 탭에서 카드 3장만 보임. 비로그인 POST 401, 버튼 → 로그인 → 돌아옴. 어울렸다 → 별로로 변경(집계 bad 1) → 다시 눌러 취소(집계 0) → 어울렸다. 음식(막국수) 화면에서 같은 조합에 내 평가·"먹어본 사람 1명" 표시. 테스트 계정·평가는 지웠다. shared 테스트 130, typecheck·build 통과.

### 회원 추천 페어링 — 회원픽 (2026-09-13)

사용자 결정: "C 집계형을 기본으로 A의 보상을 조금", 닉네임만 노출, 글 140자, 사진 1장, 홈 중앙 메뉴, 카탈로그에 없는 술·음식은 검수 후 게시.

- **입력** — 술 상세·음식 상세의 "🙌 추천하기" 버튼(`MemberPickButton`, `#recommend`). 상대(음식/술)를 카탈로그에서 검색해 고르고(정확히 같은 이름은 자동 선택), 없는 이름은 그대로 보내면 검수. 한 줄 이유(140자, 링크 금지), 사진 1장(JPG·PNG·WebP 3MB, Supabase Storage `member-picks` 공개 버킷 — 없으면 처음 올릴 때 만든다). 로그인 필수, 회원당 조합 1회, 하루 5건.
- **공개 규칙**(`packages/shared/src/pairing/member.ts`, `MEMBER_PICK_MIN = 2`) — 본인은 마이페이지 "내가 추천한 페어링"에서 즉시 본다("1명이 더 추천하면 공개돼요 (1/2)"). 같은 조합을 2명 이상 추천하면 ① 카드에 "회원 N명 추천 · 한 줄 이유 — 닉네임 · 사진" 줄 ② 그 조합이 카탈로그에 없으면 `pairings`에 `source_tier='user'`(회원픽, 전문가 85·보너스 +0.5, 근거 링크 보너스 없음 → 찰떡에는 닿지 않음) 행과 회원별 근거(`pairing_evidence` tier user, 인용 = 한 줄 이유) 생성(`lib/member-picks.ts` `syncPair`). 회원이 늘면 3명으로.
- **화면** — 홈 아이콘 메뉴 "🙌 회원 추천"(`/picks`, '수도권 술' 칸 대신)과 홈 "회원이 추천한 페어링" 섹션(공개 조합 6개, 없으면 안내). 페어링 묶음 탭에 "회원픽"(있을 때만). 마이페이지 목록에 상태 문구. 어드민 `/admin/picks`: 카탈로그에 없는 이름을 술·음식으로 지정해 게시하거나 숨김.
- **데이터** — `member_picks`(0015, RLS, 회원·조합 unique), `pairings.source_tier`에 user 허용. API `GET/POST /api/picks`(getToken), 집계는 `/api/ratings` 응답에 `picks`로 함께(화면당 요청 1회). 이벤트 `member_pick`.
- **캐시** — 회원픽 행이 생기면 `catalog_meta.version`을 올리고 `revalidatePath('/drinks/[slug]','page')`·foods·홈·/picks. `lib/catalog.ts`는 캐시가 살아 있어도 15초마다 version 한 줄을 확인해 다른 프로세스가 올린 버전을 받는다(어드민 발행에도 적용 — 예전엔 프로세스마다 5분). [실측] 한글 슬러그 경로를 개별 지정한 revalidatePath는 지워지지 않았다 → `[slug]` 페이지 전체 지정.
- **법무 메모** — 회원 글·사진이 화면에 나가므로 이용약관에 "추천 글 게시·삭제" 조항, 개인정보처리방침에 닉네임 공개 항목 필요(docs/18 §4와 함께).

**검증** [실측] — 계정 A: 폼으로 복순도가×육회 추천 → "고마워요! 1명이 더 추천하면 공개돼요 (1/2)"; API로 사진 포함 닭강정 추천(Storage URL 저장), 없는 음식 "육회비빔밥" → review, 같은 조합 재추천 409, 링크 글 거부. 계정 B: 같은 두 조합 추천 → published, 홈·/picks에 2건, 술 상세 카드 32장(회원픽 탭 1, 육회 카드 "회원 2명 추천"), 기존 닭강정 카드에 사진 포함 줄, 음식 상세(육회) 49장. 테스트 계정·추천·회원픽 행·사진은 지웠다.
