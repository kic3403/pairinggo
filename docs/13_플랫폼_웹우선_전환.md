# 13. 플랫폼 결정 변경 — 웹 우선, 이후 앱스토어·구글플레이 (2026-09-11)

docs/05의 "앱인토스 미니앱 주력" 전제를 바꾼다. 이 문서가 플랫폼에 관해서는 05보다 우선한다.

## 바뀐 결정

**웹(반응형) 먼저 열어 데이터를 쌓고 → 구매·예약 기능을 붙여 → 앱스토어·구글플레이에 출시한다.**

앱인토스는 후순위로 미룬다. 버리는 것은 아니고, 코드가 그대로 갈 수 있게 유지한다.

## 왜 바꿨나

| 항목 | 앱인토스 | 스토어 |
|---|---|---|
| 실물 술 결제 | 토스페이만 | 외부 결제 자유, 실물 상품은 인앱결제 30% 면제(애플 지침 3.1.5) |
| 로그인 | 토스 로그인만 | 자유 |
| 주류 정책 | 개발자센터 문서에 **명문 규정 없음** | 술담화·데일리샷 등 전통주 앱 선례 존재 |
| 심사 | 1~3개월, 2026년 기준 강화(기존 미니앱 재심사 포함) | 애플 수일 / 구글은 신규 개인 계정에 테스터 12명·14일 비공개 테스트 선행 |
| 획득 | 토스 앱 내 노출, 설치 불필요 | 설치 필요 |

- **결제**가 결정적이다. 최종 목표가 전통주 판매인데 앱인토스는 실물 상품에 토스페이만 허용한다.
- **불확실성이 토스 쪽에 있다.** 주류 취급 가능 여부가 문서에 없어서, 1~3개월 심사 후 거절되거나 통과 후 정책이 바뀔 수 있다. 스토어는 같은 사업 모델의 선례가 이미 있다.
- **획득은 토스가 유리**하지만, 그 이점은 판매를 못 하면 의미가 줄어든다.

## 전환 비용이 낮은 이유

앱인토스 SDK를 쓰는 파일이 3개뿐이다 — `lib/location.ts` · `lib/openExternal.ts` · `lib/analytics.ts`.
나머지는 서버 없이 도는 정적 번들이고, 이미 `inToss()`로 환경을 갈라 처리한다. CLAUDE.md 규칙으로 SDK를 한곳에 가둬 온 결과다.

## 두 화면을 나눈다

| | 공개 웹 (`apps/web`) | 앱 (`apps/miniapp`) |
|---|---|---|
| 렌더 | Next.js 서버 렌더 | 클라이언트 SPA |
| 폭 | 반응형 (모바일~데스크톱) | 모바일 고정 430px |
| 역할 | 검색 유입 수신, 색인 | 그대로 토스·스토어 앱이 됨 |
| 공유 | `packages/shared` (데이터·검색·점수) | 〃 |

미니앱을 데스크톱까지 넓히지 않는다. 어차피 앱이 될 화면이라 되돌려야 한다.

## 애플 4.2 (최소 기능) 주의

애플은 웹사이트를 그대로 감싼 앱을 거절한다. "사파리에서 열었을 때와 다를 게 없으면 앱일 이유가 없다"가 기준이다. 구글은 관대하다.

따라서 **추천 기능만 있는 상태로 애플에 올리면 위험하다.** 푸시 알림(주문 상태·예약 확정), 오프라인 열람(저장한 페어링), 위치(이미 있음) 중 최소 하나는 실제로 동작해야 한다. 구매·예약을 붙이면 푸시가 자연히 필요해지므로, 커머스 구현이 곧 4.2 통과 근거가 된다.

## 진행 순서

1. **공개 웹 페이지** — 서버 렌더·반응형 (2026-09-11 1차 완료, 아래 참고)
2. **유입 만들기** + 사업자 등록·통신판매업 신고 병행 (신고가 임계 경로다)
3. **PWA** — manifest·서비스 워커. 홈 화면 추가와 오프라인 열람의 기반
4. **구매 기능** — 데이터로 입점 우선순위를 정한 뒤. 푸시 알림 함께
5. **스토어 출시** — 구글 먼저(테스터 12명·14일 선행), 애플은 네이티브 기능을 갖춘 뒤
6. **식당 예약** — 구매가 돌아간 다음. 구매와 동시에 영업하지 않는다

앱인토스는 4번 이후 여력이 되면 같은 번들로 재개한다. 그 전에 토스 정책팀에 주류 취급 가능 여부를 문의해 두면 판단이 쉬워진다.

## 1차 구현 (2026-09-11)

`apps/web`에 공개 웹을 붙였다. 라우트 그룹 `(site)`.

| 경로 | 내용 |
|---|---|
| `/` | 랜딩 — 인기 전통주·음식, 카탈로그 규모 |
| `/drinks` | 전통주 목록 (종류별) |
| `/drinks/[slug]` | 전통주 상세 — 어울리는 음식 전체, 추천 이유, 근거 인용문·출처 링크, 구매 링크 |
| `/foods` | 음식 목록 (분류별) |
| `/foods/[slug]` | 음식 상세 — 어울리는 전통주 전체 |
| `/sitemap.xml` · `/robots.txt` | 색인 (221 URL) |

- **슬러그는 한글**이다. `/drinks/복순도가-손막걸리` — 검색 키워드가 URL에 남는다. 경로 앞부분(`drinks`·`foods`)은 영문인데, **한글 경로 세그먼트는 Next.js 정적 생성에서 `InvalidCharacterError`로 깨진다**(실측). 슬러그(동적 구간)는 한글이어도 문제없다.
- 조회는 `slugKey()`로 기호·하이픈을 무시하고 맞춘다(`packages/shared/src/slug.ts`). DB의 `slug` 컬럼과 같은 형태라 그대로 대조된다.
- 제목을 검색어에 맞췄다: "복순도가 손막걸리에 어울리는 안주 28가지". 설명·canonical·OG 포함.
- 근거가 붙은 추천과 맛 프로필로 계산한 추정을 화면에서 구분한다(docs/12 A1 대응의 일부).
- 만 19세·음주 경고 문구는 전 페이지 푸터.
- 루트 레이아웃이 `body`에 라이트 색을 인라인으로 고정하고 있어 다크 모드에서 헤더 글자가 안 보였다. 색 지정을 각 구역 CSS(`site.css`·`admin.css`)로 옮겼다.

**검증** [실측] — 빌드 통과, 7개 경로 모두 200. 상세 페이지 HTML에 페어링 카드 28개·추천 이유·근거 인용문·경고 문구가 **서버에서 렌더된 상태로** 포함(64KB). 사이트맵 221건. 데스크톱 1280px과 모바일 375px 화면 확인.

**남은 일** — PWA(manifest·서비스 워커), 검색 기능(공개 웹), 지역별 페이지, 구조화 데이터(JSON-LD), 도메인 연결 후 `SITE_URL` 환경변수 설정.
