## A. 데이터·제품 — 가장 큰 문제

### A1. 페어링의 3분의 2가 “근거 있는 주장”이 아니다 [실측]

| 출처 등급 | 건수 | 평균 점수 |
|---|---|---|
| profile (맛 프로필 계산) | 570 | 85.6 |
| media | 223 | 89.5 |
| official | 32 | 96.1 |
| sommelier | 26 | 93.2 |
| blog | 1 | 85.0 |

근거(`pairing_evidence`) 수로 보면 **0개 570건 · 1개 279건 · 2개 3건**이다. docs/11의 원칙은 “페어링은 근거가 붙은 주장”인데, 실제로는 570건이 맛 프로필 거리로 계산한 추정치다. 앱 카드에는 이 둘이 같은 모양으로 나온다.

- **지금 할 일**: `src` 배지를 사용자에게 solid하게 구분해 보여주거나(“전문가 추천” vs “맛 궁합 추정”), profile 건은 근거가 붙기 전까지 하단으로 내린다. 숨기면 852 → 282건이 되므로 커버리지와 신뢰 사이의 선택이다.
- 조합 커버리지는 108×110 중 **7.17%**. 나머지 92%는 검색해도 결과가 없다.

### A2. 검수 큐가 1인 운영 한계를 넘었다 [실측]

오늘 수집으로 후보가 **11,730건**(draft)까지 늘었다. 검수 화면은 후보 1건 = 카드 1장이므로, 10초씩 잡아도 **32시간**이다.

- 술×음식 조합으로 묶으면 **4,236개**. 카드를 조합 단위로 묶고 그 안에 근거 N개를 접어 보여주면 작업량이 **1/3**로 준다. 승격 로직(`promote`)은 이미 조합 단위로 동작하므로 UI만 바꾸면 된다.
- 언급 수 10회 이상이 3,231건, 1회가 2,187건. **언급 1~2회는 기본 숨김**으로 두고 10+부터 검수하면 상위 신호부터 빠르게 게시할 수 있다.

### A3. 규칙 기반 추출의 정밀도가 낮다 [실측]

무작위 400건 표본에서 **인용문 안에 술과 음식이 함께 등장한 것은 18%**뿐이었다. 59%는 인용문에 음식 이름조차 없다(별칭·본문 다른 위치에서 매칭).

노이즈의 정체가 분명하다.

| 음식 | 후보 수 | 문제 |
|---|---|---|
| 제철 과일 | 1,097 | “과일 발효 향”, “과일주” 같은 **맛 묘사**를 음식으로 오인 |

  이 네 가지만 넣고 재수집하면 11,730건이 2~3천 건대로 줄고 검수가 현실화된다.

## B. 미니앱

### B1. 구매 링크가 토스 밖에서 열리지 않을 수 있다 [코드] — `lib/openExternal.ts:15-19`

```ts
try { await Device.openURL(url); } catch { window.open(url, "_blank", "noopener"); }
```

`await` 뒤에 `window.open`을 호출한다. 사용자 제스처 컨텍스트가 끊긴 뒤라 팝업 차단에 걸리기 쉽다(특히 iOS Safari). 폴백이 필요한 상황이 정확히 이 경로다 — AIT Devtools 브라우저·웹 미리보기에서 “양조장 공식몰로 이동”, 근거 링크, 카카오맵 링크가 전부 조용히 실패할 수 있다. 실패해도 사용자에게 아무 표시가 없다.

또 `track()`이 열기 성공 여부와 무관하게 **먼저** 발사되어(13행) `buy_link_click` 지표가 부풀려진다. 지금 이 지표로 입점 제안을 한다면 숫자가 틀린다.

- **고칠 것**: `inToss()`로 먼저 분기해 토스 밖이면 `await` 전에 동기로 `window.open`. 실패 시 토스트. 성공/실패를 이벤트 속성으로 분리.

## C. 서버·보안

**전제**: anon 키는 코드·번들 어디에도 없다 [실측]. 미니앱은 Supabase에 직접 붙지 않고 전부 Next.js API를 거친다. 따라서 아래 RLS/RPC 항목은 **지금 당장 외부에서 악용되지는 않지만**, Phase 4에서 Supabase Auth를 클라이언트에 붙이는 순간 그대로 노출된다. 그 전에 고쳐야 한다.

### C1. `SECURITY DEFINER` 함수를 anon이 실행할 수 있다 [실측] — P0

| 함수 | security definer | anon 실행 | search_path |
|---|---|---|---|
| `refresh_popular_terms` | true | **true** | 미설정 |
| `refresh_pairing_feedback` | true | **true** | 미설정 |

두 함수 모두 본문에 `delete ... where true`가 있다. PostgREST는 public 스키마 함수를 `POST /rest/v1/rpc/<name>`으로 노출하므로, anon 키를 가진 사람이 `popular_terms`를 비우거나 전체 스캔을 반복 호출할 수 있다. `search_path` 미설정은 Supabase 린터도 잡는 권한 상승 벡터다.

- **고칠 것**: `revoke execute ... from public, anon, authenticated` + `alter function ... set search_path = public, pg_temp`. 크론은 service_role이라 영향 없다.

### C2. RLS가 API 필터보다 느슨하다 [실측]

| 테이블 | 정책 | 결과 |
|---|---|---|
| `pairings` | `status <> 'hidden'` | **pending(검수 중)도 읽힘** — API는 curated/ai만 내보내는데 |
| `pairing_evidence` | `true` | 인용문·URL·추천자 전부 읽힘 |
| `sources` | `true` | 전부 읽힘 |
| `events`, `search_logs`, `pairing_candidates`, `popular_terms` | 정책 0개 | RLS 켜짐 + 정책 없음 = **차단됨(정상)** |

후보 큐는 안전하다. `pairings`의 pending 노출과 `pairing_evidence` 전체 공개만 좁히면 된다.

### C3. 발행을 되돌릴 방법이 없다 → **2026-09-11 수정 완료**

**고친 내용**
- `publish()` 순서를 **스냅샷 → counts → version**으로 바꾸고 세 단계 모두 에러를 확인한다. 이제 스냅샷 저장이 실패하면 버전이 올라가지 않아 "무엇을 발행했는지 모르는 상태"가 생기지 않는다.
- `pnpm db:rollback` 추가. 인자 없이 실행하면 발행 이력, 버전을 주면 **무엇이 바뀌는지만** 보여주고(기본 미적용), `--apply`를 붙여야 실제로 적용한다. 페어링을 지우지 않고 스냅샷 이후 추가분만 `pending`으로 내리므로 근거·검수 이력이 보존된다. 적용은 한 트랜잭션이고, 끝나면 되돌린 내용으로 새 버전을 발행한다.
- 어드민 발행 화면에 **발행 이력 표**(최근 10건·현재 버전 표시)와 되돌리는 방법을 넣었다.
- 원클릭 롤백 버튼은 **넣지 않았다.** C5(관리자 인증 취약)가 아직 그대로라, 공유 비밀번호 하나로 파괴적 동작을 실행할 수 있게 만드는 것은 위험하다. 인증을 고친 뒤에 붙이는 편이 맞다.

**검증** [실측] — 852건 → 851건 시점으로 dry-run 시 추가된 `d01 × f10` 1건을 정확히 찾아냈고, 없는 버전·현재 버전·변경 없음 경로를 확인했다. 바뀌는 필드(점수·등급·이유)를 "지금 → 되돌린 뒤"로 보여준다.

- `catalog_snapshots`는 저장만 하고 **읽는 코드가 어디에도 없다.** 롤백 스크립트도, 어드민 버튼도 없다. 잘못 발행하면 프로덕션에 SQL을 직접 쳐야 한다.
- 중간의 `counts` upsert는 에러를 확인하지 않는다.
- **고칠 것**: 스냅샷 먼저 → 버전 나중, 가능하면 Postgres 함수 하나로 묶어 원자적으로. `db:rollback <version>` 스크립트와 어드민의 “이전 버전으로” 버튼.

</details>

### C4. 카탈로그 조회에 limit이 없다 → **2026-09-11 수정 완료**

**고친 내용** — `lib/catalog.ts`에 `selectAll()`을 두어 네 테이블(drinks·foods·pairings·pairing_evidence)을 1,000행씩 끝까지 받아온다. 10만 행 상한에 걸리면 "데이터가 잘렸다"고 크게 로그를 남긴다.

### C5. 관리자 로그인 [코드]

- 시도 횟수 제한·잠금·로깅이 없다. `rateLimit()`은 places 라우트에만 걸려 있다.
- `ADMIN_SECRET`이 없으면 HMAC 키가 **비밀번호 그 자체**다(`admin-auth.ts:10`). 현재 `.env.local`에 `ADMIN_SECRET`이 없다 [실측]. 쿠키 하나가 유출되면 비밀번호를 오프라인에서 역산할 수 있다.
- `checkPassword`가 `pw.length`(UTF-16)와 `Buffer` 바이트 길이를 섞어 쓴다. **한글 비밀번호를 입력하면 `timingSafeEqual`이 throw해 500**이 난다. 현재 비밀번호는 ASCII 20자라 당장은 안 터지지만, 한글로 바꾸면 로그인 자체가 깨진다.
- `secure` 플래그를 요청 URL 프로토콜로 정한다 — 프록시 뒤에서 http로 보이면 7일짜리 세션 쿠키가 평문으로 나간다.
- 로그아웃이 GET이고 서버 측 무효화가 없다(탈취된 토큰은 7일 유효).

### C6. 공개 쓰기 API에 제한이 없다 [코드]

`POST /api/v1/events`(최대 100행/요청)와 `GET /api/v1/search`(호출마다 로그 1행) 모두 레이트 리밋이 없다. `events`는 `refresh_pairing_feedback`을 거쳐 점수에, `search_logs`는 `popular_terms`를 거쳐 **앱 인기 검색어와 어드민 대시보드의 “수집 우선순위”**에 직접 반영된다. 즉 외부에서 추천 신호와 운영 로드맵을 밀어넣을 수 있다. 보존 정책(TTL)도 없어 무한히 쌓인다.

`events`의 본문 크기 검사는 `Content-Length` 헤더만 본다 — `Transfer-Encoding: chunked`면 0으로 읽혀 우회된다.

### C7. 서버리스에서 무의미한 메모리 캐시·리미터 [코드]

`kakao.ts`의 `buckets`(레이트 리밋)와 `cache`, `catalog.ts`의 5분 캐시가 전부 인스턴스 메모리다. Vercel이 인스턴스를 늘리면 “분당 30회”는 `30 × 인스턴스 수`가 된다. `buckets`는 정리 코드가 없어 IP마다 영구히 쌓인다. 식별자도 `x-forwarded-for`(클라이언트 조작 가능)를 쓴다.

카카오 호출은 요청 1건당 최대 4회(식당) / 3회(판매점) 발생하고, 캐시 키가 좌표를 소수 3자리로만 끊어 **0.001씩 올리면 캐시를 100% 우회**할 수 있다. 유료 쿼터가 소진되면 전 사용자의 식당 검색이 죽는다.

### C8. DB 장애가 5분간 캐시된다 [코드] — `lib/catalog.ts:43-57`

Supabase가 30초 끊기면 정적 폴백 결과가 **5분 TTL로 캐시**되고, CDN에는 `s-maxage=300, stale-while-revalidate=3600`이 붙는다. 그 사이 `version`이 `static-xxxx`로 바뀌므로 **모든 미니앱이 카탈로그를 번들 스냅샷으로 되돌렸다가 나중에 다시 되돌린다.** 그동안 최근 승격된 페어링이 사라진다. 실패는 15초쯤만 캐시하고, 폴백이 version을 바꾸지 않게 해야 한다.

### C9. `promote`가 트랜잭션이 아니다 [코드] — `lib/admin-data.ts:52-85`

PostgREST 호출 6개가 순차 실행된다. 라우트가 `tier`를 검증하지 않아(`String(b.tier || "blog")`) 잘못된 등급이 오면 **pairings 행을 먼저 만든 뒤** evidence 삽입이 CHECK 제약에 걸려 실패한다 → 근거 0개짜리 pending 페어링이 고아로 남는다. 두 사람이 같은 조합을 동시에 승격하면 unique 위반으로 한 쪽이 실패한다.

`assignEntity`는 `promoted`/`rejected` 후보에도 상태를 무조건 `draft`로 되돌려, 이미 승격된 건이 큐에 다시 나타나 중복 승격될 수 있다.

### C10. 검색 로그가 유실된다 [코드] — `search/route.ts:29`

`void sb.from("search_logs").insert(...)`를 await하지 않고 `after()`도 쓰지 않는다. Vercel은 응답 직후 인스턴스를 얼리므로 콜드 인스턴스에서는 이 insert가 완료되지 않는다. 검색 로그 1건뿐인 현재 수치의 일부는 이 버그일 수 있다.
