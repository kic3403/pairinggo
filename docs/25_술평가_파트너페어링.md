# 25. 술 평가(별점·한줄평) + 파트너 페어링 입력 (2026-09-26)

데일리샷·비비노·캐치테이블 비교 분석에서 고른 두 가지(사용자 결정 2026-09-26: "2번·4번 먼저").
- **2번 술 단위 별점·한줄평** — 비비노·데일리샷의 힘은 상품마다 쌓인 별점 수. 우리 '먹어봤어요'는 조합 단위 3단계뿐이라 술 상세 상단이 비어 있었다.
- **4번 파트너가 직접 넣는 페어링** — 근거 있는 페어링이 12%(613/4,987)뿐. 양조장 파트너가 "우리 술에 어울리는 음식"을 적으면 검수 없이 **양조장 공식(official)** 근거로 게시된다. 가장 싼 근거 확장 경로.

## 1. 술 평가 `drink_reviews` (0038)
- 표: `drink_reviews(id, drink_id, user_id, stars 1~5, body ≤140, status active|hidden, hidden_reason, created_at, updated_at)`, `unique(drink_id, user_id)` — **회원당 술 하나에 평가 하나**(수정·삭제 가능). 탈퇴는 cascade.
- 규칙 `shared/pairing/drink-review.ts`(테스트): `drinkReviewProblem({stars, body})`(정수 1~5, 140자, 링크·이메일 금지), `summarizeStars(stars[])`(평균 소수 1자리·분포, **3명 미만이면 평균을 감춘다** `DRINK_REVIEW_MIN_N`), 하루 상한 `DRINK_REVIEWS_PER_DAY` 20.
- 서버 `lib/drink-reviews.ts`, API `/api/drink-reviews`(GET ?d= 요약+최근 20+내 평가 / POST {d, stars, body} upsert / DELETE {d}). 세션은 `getToken`(auth()는 첫 화면 로그아웃과 경합, docs/13).
- 화면: 술 상세 머리 카드에 **"★ 4.3 · 회원 12명"** 줄(3명 이상일 때, `#reviews`로 이동) — 외부 평점(`ext_rating`)·근거 등급과는 줄을 따로 두고 "회원" 표기. 페어링 카드 아래 `DrinkReviews` 칸(별 5개 + 한 줄 + 최근 평가 목록, 로그인 안 했으면 로그인 링크). 등급·근거 점수에는 섞지 않는다(CLAUDE.md 규칙).
- 구조화 데이터: 3명 이상이면 Product에 `aggregateRating`(검색 결과 별점).
- 어드민 `/admin/drink-reviews`: 최근 목록, 숨기기(사유)·복구. 신고 기능은 아직 없음(회원 수가 늘면 식당 리뷰처럼).
- 방침: "서비스를 이용할 때" 수집 항목과 공개 항목에 **술 평가(별점·한 줄)** 문구 추가. 이미 동의한 '먹어봤어요 평가·회원 추천 글'과 같은 성격(닉네임 공개 콘텐츠)이라 동의 버전은 올리지 않는다.

## 2. 파트너 페어링 `partner_pairings` (0038)
- 표: `partner_pairings(id, merchant_id, drink_id, food_id, note ≤120, pairing_id, evidence_id, created boolean(우리가 pairings 행을 새로 만들었는지), prev jsonb(기존 행의 tier·es·reason 스냅샷), created_at, updated_at)`, `unique(merchant_id, drink_id, food_id)`.
- 누가: **양조장 파트너**(`merchants.kind = brewery`)가 `merchants.brewery`로 고른 카탈로그 양조장의 술에만(그 술의 `brewery_name`이 같아야). 술당 최대 `PARTNER_PAIRING_MAX_PER_DRINK` 8개.
- 규칙 `shared/pairing/partner-pairing.ts`(테스트): `partnerPairingProblem`, `partnerEvidence(brewery, note)` → `{source: "○○ 제공", who: 양조장, quote: note, tier: official}`, `applyPartnerPairing(existing, note, brewery)` → 기존 행이 official·sommelier면 등급·점수 유지(근거만 추가), 그 외(profile·blog·media·user·없음)는 **official로 올리고 점수 max(기존, 90)**, 이유는 파트너 한 줄(없으면 "○○이 직접 추천한 조합입니다").
- 서버 `packages/server/src/partner-pairings.ts`: `listPartnerPairings`·`savePartnerPairing`(upsert → pairings 동기화 → 근거 행 → `catalog_meta.version` 올림)·`removePartnerPairing`(근거 삭제, 우리가 만든 행이면 삭제·아니면 prev로 되돌림). 웹 카탈로그 캐시는 15초 안에, 상세 화면(ISR)은 최대 10분 안에 반영.
- 파트너 앱 `/pairings` 탭(양조장만): 우리 술마다 음식 고르기(카탈로그 음식 datalist) + 한 줄 이유 + 추가, 줄마다 삭제. `POST/DELETE /api/pairings`.
- 손님 화면: 기존 페어링 카드가 그대로 **"양조장 공식"** 배지 + 근거 줄("○○ 제공 — ○○")로 보여 준다. 새 화면 없음.

## 3. 검증
- Vitest(규칙·요약·구조화 데이터), 웹·파트너 타입 검사, 로컬 캡처(술 상세 평가 칸·머리 카드 별점 줄, 파트너 페어링 화면), API 시험(미로그인 401·잘못된 값 400·하루 상한), 파트너 페어링 저장 뒤 술 상세에 공식 배지가 붙는지.

## 4. 검증 결과 (2026-09-26)
- Vitest 472 통과(규칙·요약·구조화 데이터), 웹·파트너 타입 검사 통과. 운영 DB에 0038 적용.
- 술 평가 API: 미로그인 401 · 별점 6 → "별점은 1~5" · 링크 → 거부 · 저장 → 3명 평균 4.7 · 같은 회원 재저장은 수정(인원 그대로). 화면: 머리 카드 "★ 4.7 회원 평가 3명", 평가 칸(분포 막대·내 평가 고치기/지우기·최근 목록), 어드민 목록. 시험 평가는 지웠다.
- 파트너 페어링 API: 미로그인 401 · 다른 양조장 술 → "우리 양조장 술만" · 없는 음식 → 거부 · 저장 → pairings 행 official 90 + 근거 "한증류소 제공" → 술 상세 카드에 **전문가픽 · 양조장 공식 · 한증류소 제공**과 한 줄 이유 표시 · 삭제 → 우리가 만든 행이라 pairings 행도 삭제. 파트너 `/pairings` 화면(휴대폰·데스크톱) 확인.

## 5. 못 찾는 검색 입구 — 라벨 사진으로 찾기 + 추가 요청 (2026-09-26, 분석 1번)
검색 99건 중 30건이 결과 없음이었다. 비비노의 "라벨을 찍으면 무조건 찾아진다"에 대응하는 우리 입구 두 가지.
- **라벨 사진으로 찾기** `LabelSearch`(검색 화면 검색창 아래 작은 버튼, 결과가 없을 때는 빈 결과 칸에 크게): 사진을 고르면 브라우저에서 긴 변 1,280px JPEG로 줄여 `POST /api/v1/label-read` → `packages/server/label-read.ts`가 Claude(`claude-opus-5`, 구조화 출력, 카탈로그 술 이름을 system에 넣어 캐시)로 제품명 후보·양조장·도수·`catalog_name`을 읽고 → `lib/label-read.ts`가 shared `search`(부분 일치·오타)로 대조해 5개까지(점수 55 이상, `catalog_name`과 같은 이름은 "라벨과 같은 제품"). 못 찾으면 읽은 이름이 채워진 요청 폼. **사진은 저장하지 않는다.** 읽은 이름은 `search_logs`(찾음 = `label-hit`, 못 찾음 = `search_empty`/`label`)에 남겨 대기열에 오른다. 상한: IP당 분당 4번, 하루 전체 300번(`LABEL_READS_PER_DAY`, Claude 비용). 실측: 파트너가 올린 '감싸주는 날' 병 사진 → 이름 2개 읽고 d108 정확히 찾음.
- **추가 요청** `DrinkRequestForm` + `drink_requests`(0039): 이름 2~60자 + 메모 140자(링크 금지), 로그인 선택 — 회원은 하루 10건·같은 이름 열린 요청은 하나로, 비회원은 IP당 분당 5번. 규칙 `shared/drink-request.ts`. 운영자는 `/admin/wanted` 맨 위 "회원 요청" 표에서 술을 넣은 뒤 **등록됨**(카탈로그 술 선택) 또는 **보류**(사유) → 요청한 회원은 마이페이지 "내가 요청한 술"에서 "등록됨 · 이름 → 보러 가기"로 본다. 열린 요청은 대기열 `buildWantedList`에 source `request`(무게 4, 가장 무거움)로 합쳐진다.
- 방침: 수집 항목에 "술 추가 요청(이름·메모), 라벨 사진에서 읽은 술 이름(사진은 저장하지 않음)" 추가(동의 버전 그대로 — 검색어와 같은 성격).
- 검증: Vitest 475, 웹 타입 검사 통과, 0039 운영 적용. API: 짧은 이름·링크 거부, 비회원·회원 저장, 회원 중복 요청은 같은 id, 분당 상한 429, 어드민 처리(없는 술 id 거부·미로그인 401). 화면: 빈 결과(390·1280), 결과 있는 검색의 작은 버튼, 마이페이지 "등록됨 · 감싸주는 날 · 보러 가기", 어드민 회원 요청 표 + 대기열 "요청 1" 태그. 시험 데이터는 지웠다.
