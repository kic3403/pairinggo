# 앱 점검 리포트 2차 (2026-09-12)

1차 리포트(docs/12, 2026-09-11) 이후 공개 웹·회원·검색·구매·관심지역·일일 트렌드까지 붙은 상태를 다시 훑었다.
표기: [실측] = 이 세션에서 직접 확인, [코드] = 코드 읽고 판단. 1차에서 해결된 항목(B1·C3·C4·C4-1)은 뺐다.

## 0. 한 줄 요약

사용자가 볼 화면과 기능은 대체로 갖춰졌다. 지금 가장 큰 구멍은 **(1) 웹에서 아무 기록도 남지 않아 "데이터를 쌓는다"는 목표가 작동하지 않는 것, (2) 로그인은 되는데 개인정보 문서가 없는 것, (3) 3분의 2 페어링이 여전히 근거 없는 주장인 것** 세 가지다. 지인 배포 전에 1·2를 막고, 데이터는 꾸준히.

## A. 목표와 어긋난 것 — 먼저 막을 구멍

### A1. 공개 웹은 기록을 남기지 않는다 [실측] — P0 → **2026-09-12 해결** (docs/13 "웹 퍼널 기록")
- 검색 페이지는 서버에서 검색 엔진을 직접 돌려서 `search_logs`에 아무것도 남기지 않는다. `/api/v1/search`(미니앱용)만 로그를 쓴다. → `popular_terms`가 비어 있고, 어드민 대시보드의 "없는 검색어 상위 20"도 웹 사용자에게서는 안 채워진다.
- 구매 링크(`구매 ↗`)를 눌러도 `buy_link_click` 이벤트가 없다. `<a target=_blank>` 그대로다. 입점 제안 자료와 `refresh_pairing_feedback` 입력이 0인 채로 남는다.
- 맛집 찾기·판매점 찾기·하트도 이벤트가 없다(하트는 `saved_items`에 남으니 예외).
- 고치는 법: 검색 페이지 서버 컴포넌트에서 `search_logs` insert(비동기, 실패 무시) + 웹용 `track()`(클릭 시 `navigator.sendBeacon('/api/v1/events')`) + 구매 링크를 `BuyLink` 클라이언트 컴포넌트로. 미니앱 `openExternal.ts` 규칙(열렸을 때만 기록)을 웹에도 같은 원칙으로. 반나절.

### A2. 개인정보처리방침·이용약관·수집 동의가 없다 [실측] — P0 (지인 배포 전)
- 이메일·닉네임·저장 목록·위치(관심지역은 기기 저장이라 제외)를 받는데 `/privacy`·`/terms` 페이지가 없고 가입 화면에 동의 체크가 없다. 개인정보보호법상 수집 항목·목적·보관기간·제3자 제공(주문 시 양조장)·위탁(Vercel·Supabase·카카오 로컬)을 고지해야 한다.
- 카카오·네이버·구글 로그인 검수도 이 페이지 URL을 요구한다.
- 고치는 법: 정적 페이지 2개 + 가입 폼 체크박스 2개(필수: 이용약관·개인정보, 선택: 없음) + `users.agreed_at` 컬럼. 문안은 초안을 내가 만들고 검토는 사용자가.
- **2026-09-12 추가**: 가입 때 성별·생년월일·시도를 받고 로그에 회원 id를 붙이기 시작했다(docs/13). 수집 항목이 늘었으므로 방침 문안에 반드시 포함. 지인 배포 전 처리.

### A3. 페어링 근거 공백 그대로 [실측] — 1차 A1 재확인
- 852건 중 근거(ev) 있는 것은 여전히 3분의 1 수준. 후보 11,730건은 검수 대기. 규칙 추출 정밀도(1차 A3)도 그대로.
- 지금 상황 검색·홈이 "근거와 함께"를 내세우는데 카드 3개 중 2개는 맛 프로필 계산이다. 화면에서는 `profile` 배지로 구분되지만 첫인상은 과장이다.
- 제안: (a) 인기 상위 30종부터 근거 2개씩 채우는 "집중 검수 주간"(후보 큐를 술별로 묶어 보는 화면 = 1차 A2), (b) 상황 검색 카드에서 `profile` 페어링은 "맛 프로필 추정"이라고 문장으로 쓰기.

### A4. "맛집"이라는 말이 근거 없이 쓰인다 [실측] — 2026-09-12 일부 보완: 미쉐린 배지(docs/17). 문구·자체 신호는 그대로 남음
- 카카오 로컬은 별점·리뷰를 주지 않는다. 지금 "맛집 찾기"는 "육회 파는 음식점 목록"이다(이 세션에서 설명함).
- 제안: 문구를 "주변 음식점"으로 바꾸고, 우리 신호(하트 저장 수·길찾기/전화 클릭 수)를 식당별로 집계해 "저장 12 · 길찾기 30"처럼 표시. A1이 선행.

## B. 회원·보안

### B1. 관리자 로그인에 시도 제한이 없다 [코드] — 1차 C5
- `/admin/api/login`은 비밀번호만 맞으면 된다. 이메일 로그인은 10회/15분 잠금이 있는데 어드민은 없다. 같은 방식으로 IP당 10회/15분(메모리 → 서버리스에서 약함 → `users`처럼 DB 테이블에 기록).

### B2. `refresh_*` 함수 anon 실행 권한 [코드] — 1차 C1, P0
- 아직 회수 안 됨. `revoke execute on function refresh_popular_terms, refresh_pairing_feedback from anon, authenticated;` 마이그레이션 한 줄.

### B3. 세션 초기화 정책의 부작용 [코드]
- 첫 화면 무조건 로그아웃(사용자 결정)은 "링크를 새 탭에서 열기"에는 안 걸리고, 같은 탭에서 도메인이 바뀌었다 돌아오면 유지된다. 의도와 맞는지 한 번 더 확인. 나중에 "로그인 유지" 체크박스로 사용자에게 선택권을 주는 편이 이탈이 적다.

### B4. 비밀번호 재설정이 없다 [코드]
- 이메일 가입자가 비밀번호를 잊으면 방법이 없다. 이메일 발송 수단(Resend 등 무료 3,000통/월)이 필요. 소셜 로그인 키가 들어가기 전까지는 이메일 계정이 전부라 우선순위 높음.

### B5. 회원 탈퇴가 없다 [코드]
- 개인정보보호법상 필요. 마이페이지에 "탈퇴" → `users` 삭제(cascade로 `saved_items`).

### B6. 공개 쓰기 API 제한 [코드] — 1차 C6
- `/api/v1/events`·`/api/saved`에 IP 제한이 없다. 카카오 로컬만 분당 30회. 서버리스 메모리 리미터는 인스턴스마다 따로라 약하다(1차 C7). Vercel WAF 무료 규칙 또는 Upstash 무료 티어.

## C. 데이터·순위

### C1. 일일 트렌드의 빈 자리 [실측]
- 유튜브는 첫날 20종만(할당량), 인스타는 수동, 구글은 키 없음. 며칠간은 네이버 블로그 위주 순위다. 채널이 채워지기 전까지 배너 문구가 그 사실을 보여 주긴 한다.
- 할 일: Vercel에 5개 키 등록(사용자), 구글 검색엔진 만들기(사용자), 인스타 CSV 주 1회(사용자). 크론 실패 알림(1차 D3)은 아직 없음 → 응답 `ok:false`면 이메일/카카오톡 알림.

### C2. 술 사진이 한 장도 없다 [실측]
- 홈 배너·카드가 병 실루엣이다. aT 사진은 상업 이용 불가. 양조장에 사진 제공 요청(이메일 템플릿) → `image_url`에 넣는 운영 절차가 필요. 양조장 입장에서는 노출이라 대개 준다. 상위 30종부터.

### C3. 음식 데이터가 얕다 [코드]
- 음식 110종은 태그·프로필뿐이고 설명 문장·대표 사진·조리 방식(구이/탕/회)이 없다. 음식 상세는 페어링 목록만이라 검색 유입 페이지로 약하다.

### C4. 지역 데이터가 시군구까지 고르지 않다 [실측]
- 서울 7종 중 상당수가 "서울"까지만. 강남·서초 같은 동 단위 관심지역은 대부분 "서울 전체 기준"으로 떨어진다. 양조장 주소를 `packages/db/research/` 자료로 채우면 된다(지역별 목록 엑셀에 주소가 있음).

## D. 웹 품질

### D1. 오류·없음·로딩 화면이 없다 [실측]
- `error.tsx`·`not-found.tsx`·`loading.tsx`가 하나도 없다. 없는 술 주소는 Next 기본 404(영문), DB 장애는 빈 화면. 미니앱의 ErrorBoundary 부재(1차 B2)도 그대로.

### D2. SNS 공유 이미지가 없다 [실측]
- OG 태그는 있지만 `opengraph-image`가 없어 카카오톡에 링크를 보내면 이미지 없는 카드다. 지인 배포에서 첫 클릭률에 직접 영향. 술 상세는 이름·종류·도수를 넣은 자동 생성 이미지(Next `ImageResponse`) 한 파일이면 된다.

### D3. PWA·홈 화면 추가 없음 [실측]
- `manifest`·아이콘·서비스워커 없음. 앱스토어 출시 전 단계로 "홈 화면에 추가"가 있으면 재방문이 쉽다. 반나절.

### D4. 이미지 없는 목록의 시각 밀도 [실측]
- 흰 바탕으로 바꾼 뒤 카드가 글자만이라 단조롭다. C2(사진)가 근본 해법이고, 그전에는 카테고리 색 점·도수 눈금 같은 작은 시각 요소로 보완.

### D5. 접근성 [코드]
- 지역 설정 시트에 포커스 가두기(focus trap)가 없다. ESC·배경 클릭은 된다. 하트 버튼의 상태 읽기(`aria-pressed`)는 있음. 마퀴는 `prefers-reduced-motion` 대응 있음.

### D6. 검색 품질 [코드]
- "지역 + 전통주"는 됐지만 "달달한 막걸리", "도수 낮은 술" 같은 형용사 검색은 상황 검색 규칙에 일부만 있다. `search_logs`가 쌓이면(A1) 못 찾은 검색어 상위부터 규칙을 늘린다.

## E. 운영

### E1. 테스트·CI 없음 [실측] — 1차 D1
- 테스트 100건은 있지만 GitHub Actions가 없어 푸시 전에 사람이 돌려야 한다. `pnpm typecheck && pnpm test` 워크플로 1개.

### E2. 관측 [코드] — 1차 D2
- Vercel 로그뿐. 5xx·크론 실패·카카오 429를 알 방법이 없다. Sentry 무료 티어 또는 Vercel 로그 드레인.

### E3. 백업 [코드] — 1차 D4
- Supabase 무료 티어는 자동 백업이 없다. `pnpm db:export`를 주 1회 크론(GitHub Actions)으로 돌려 JSON을 저장소에 커밋하면 카탈로그는 복구 가능. `users`·`saved_items`는 별도 덤프 필요.

### E4. 미니앱과 웹의 기능 격차 [코드]
- 미니앱에는 관심지역·지역별 술·최근 검색·연관 추천이 있고 웹에는 회원·하트·구매·마이·트렌드 배너가 있다. 앱스토어 출시용 앱을 웹으로 감쌀 계획이라면 미니앱 코드는 앱인토스 제출 때까지 동결하고 웹에 집중하는 편이 낫다. 두 곳을 동시에 키우면 어긋난다.
